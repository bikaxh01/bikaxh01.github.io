Understanding Rate Limiting in Python: A Practical Guide

If you’ve ever built an API, chances are you’ve heard about rate limiting. Almost every production application uses it in one form or another. Whether it’s a login endpoint, a payment service, or an AI-powered API, you need a way to prevent clients from sending an unlimited number of requests.

Imagine you launch your application today. Within a few hours, a script starts sending thousands of requests every second to your /login endpoint. Even though those requests are invalid, your server still has to process each one. Before long, your CPU usage spikes, your database is under pressure, and genuine users begin experiencing slow responses.

This is exactly the kind of problem rate limiting is designed to solve.

In this blog, we’ll understand what rate limiting is, how to decide who should be rate limited, and then dive into the most common algorithms used in production systems.

Note: In this article, we’ll focus on understanding the concepts behind each algorithm. In the next blog, we’ll build a production-ready FastAPI application using Redis and the limits library, implementing each algorithm on its own endpoint.

What is Rate Limiting?

Rate limiting is a technique that restricts how many requests a client can make within a specific period of time.

For example, you might decide that a client can only make:

  • 5 requests per minute
  • 100 requests per hour
  • 1000 requests per day

If the client stays within the limit, every request is processed normally. Once the limit is exceeded, the server responds with an error (typically HTTP 429 - Too Many Requests) until the limit resets or enough time has passed.

Think of it as setting rules for your API.

Instead of saying:

“Send as many requests as you want.”

you’re saying:

“You can send five requests every minute. After that, you’ll need to wait.”

This protects your application from abuse while ensuring everyone gets a fair share of your server’s resources.

Rate limiting is commonly used to:

  • Prevent brute-force attacks on login endpoints.
  • Protect APIs from abuse and spam.
  • Avoid accidental traffic spikes caused by buggy clients.
  • Reduce infrastructure costs, especially for expensive AI endpoints.
  • Ensure one user doesn’t consume all available resources.

Before Choosing an Algorithm…

Most people jump straight into learning algorithms like Fixed Window or Token Bucket.

But there’s a more important question you need to answer first.

Who exactly are we rate limiting?

A rate limiting algorithm only counts requests. It doesn’t know whose requests those are. That’s your responsibility.

The identifier you choose depends on the type of endpoint you’re protecting.

Let’s look at the most common approaches.

1. Rate Limiting by IP Address

The simplest approach is to use the client’s IP address.

Every incoming request already contains the client’s IP, making it an easy identifier even before the user logs in.

For example:

192.168.1.15

or

103.22.xx.xx

Every request coming from the same IP contributes to the same rate limit.

This works well for public endpoints like:

  • /login
  • /register
  • /forgot-password

because the user hasn’t authenticated yet, so you don’t have a user ID to work with.

However, IP-based rate limiting has a major limitation.

The Shared IP Problem

Imagine a college campus with hundreds of students connected to the same Wi-Fi network.

Although there are hundreds of users, the outside world only sees a single public IP address assigned to the college router.

Now suppose your API allows:

100 requests per minute

One student accidentally runs a script that sends thousands of requests.

Very quickly, that shared IP reaches the limit.

Now every other student connected to the same Wi-Fi starts receiving:

HTTP 429 Too Many Requests

even though they never abused your API.

This is called the Shared IP Problem.

The same issue can happen in:

  • Schools and universities
  • Corporate offices
  • Hotels
  • Coffee shops
  • Mobile carrier networks
  • Users behind NAT (Network Address Translation)

That’s why IP-based rate limiting is great for unauthenticated endpoints, but it’s usually not the best choice once a user has logged in.

2. Rate Limiting by User ID

Once a user is authenticated, every request carries information about who is making it.

Instead of using the client’s IP address, we can simply use the authenticated user’s ID.

For example:

User ID: 42

Now every user gets their own independent rate limit.

This solves the shared IP problem because two users on the same Wi-Fi no longer affect each other’s request quota.

For authenticated APIs, this is usually the preferred approach.

Common examples include:

  • /me
  • /profile
  • /posts
  • /orders
  • /notifications

Each user is treated independently, regardless of where they’re accessing the API from.

3. Rate Limiting by User ID + Endpoint

Not every endpoint has the same cost.

Consider these two APIs:

GET /profile

and

POST /generate-image

Fetching a profile might take only a few milliseconds.

Generating an AI image could take several seconds, consume GPU resources, and cost you money.

If both endpoints share the same rate limit, a user could spend their entire quota calling /profile and still be unable to generate an image.

A better approach is to include both the user and the endpoint in the rate limit key.

For example:

user:42:/generate-image

or

user:42:/chat

This gives you much finer control over expensive APIs.

Many AI applications use this strategy because different endpoints have very different infrastructure costs.

4. Rate Limiting by API Key

If you’re building a public API for third-party developers, the best identifier is usually the API key.

Each developer receives their own API key:

sk_live_xxxxxxxxx

Every request made using that key contributes to its own rate limit.

This allows you to offer different plans with different quotas.

For example:

PlanLimit
Free100 requests/day
Pro10,000 requests/day
EnterpriseCustom

This approach is widely used by companies that expose APIs to external developers.

A Practical Strategy

In production, it’s common to combine multiple strategies rather than relying on just one.

A simple and practical approach looks like this:

EndpointIdentifier
/login, /register, /forgot-passwordIP Address
Authenticated APIsUser ID
Expensive AI endpointsUser ID + Endpoint
Public APIsAPI Key

There’s no universal rule here. The right choice depends on your application and the type of traffic you’re handling.

The important thing is to choose an identifier that’s both fair to users and effective at protecting your backend.

Now that we’ve answered who we’re rate limiting, it’s time to answer the next question:

How do we actually enforce those limits?

In the next section, we’ll start with the simplest and most commonly taught algorithm: Fixed Window Rate Limiting. We’ll build it from scratch, understand why it works, and also see where it falls short.

Fixed Window Rate Limiting

Let’s start with the simplest rate limiting algorithm.

Suppose your API allows:

5 requests per minute

At first, you might think we need to store the timestamp of every request.

Turns out, we don’t.

For this algorithm, we only care about one thing:

How many requests has this user made in the current one-minute window?

That’s it.

We don’t care whether those requests happened at the beginning of the minute or at the end. As long as they’re inside the same one-minute window, they all contribute to the same counter.

This makes Fixed Window extremely simple to understand and implement.

Building It Step by Step

Forget about Redis for a moment.

Imagine you’re writing everything in plain Python.

The first thing we need is somewhere to store the request count for each user.

A dictionary works perfectly.

requests = {
    "user_1": 3,
    "user_2": 5,
}

This tells us:

  • user_1 has already made 3 requests.
  • user_2 has already made 5 requests.

Now another request arrives from user_1.

The first thing we do is read their current count.

count = requests.get("user_1", 0)

Suppose the result is:

count = 3

Our limit is:

5 requests per minute

Since the user hasn’t reached the limit yet, we allow the request and increment the counter.

requests["user_1"] += 1

Now our dictionary becomes:

requests = {
    "user_1": 4,
    "user_2": 5,
}

Pretty simple.

But there’s an obvious question.

Wait… Where Does “Per Minute” Come From?

Right now, our counter keeps increasing forever.

If someone makes five requests today, they’ll never be able to make another request tomorrow.

Clearly, that’s not what we want.

We somehow need the counter to reset after one minute.

One way to do that is to store an expiration time along with the counter.

Instead of storing only this:

{
    "user_1": 4
}

we store:

{
    "user_1": {
        "count": 4,
        "expires_at": 1710000060
    }
}

Now every incoming request follows roughly this flow:

  1. Read the user’s record.
  2. Check whether the current time is greater than expires_at.
  3. If it is, reset the counter.
  4. Otherwise, continue using the existing count.

Conceptually, it looks like this:

if current_time > expires_at:
    count = 1
    expires_at = current_time + 60
else:
    count += 1

This gives us fixed one-minute windows.

For example:

12:00:00 → 12:00:59
12:01:00 → 12:01:59
12:02:00 → 12:02:59

Every request inside the same window contributes to the same counter.

Doing This in Redis

In production, we usually don’t manage expiration timestamps ourselves.

Redis already gives us exactly what we need through key expiration (TTL).

The flow becomes much simpler.

  • Increment the user’s counter.
  • If this is the first request, set a TTL of 60 seconds.
  • Redis automatically deletes the key after the TTL expires.

No manual cleanup.

No background jobs.

No expiration checks.

Redis handles everything for us.

That’s one of the reasons Redis is the most popular choice for implementing rate limiters.

Python Example

Here’s a simplified implementation using the limits library.

from limits import storage
from limits.strategies import FixedWindowRateLimiter
from limits import RateLimitItemPerMinute

store = storage.MemoryStorage()

limiter = FixedWindowRateLimiter(store)

limit = RateLimitItemPerMinute(5)

user = "user_42"

if limiter.hit(limit, user):
    print("Request Allowed")
else:
    print("Rate Limit Exceeded")

In the next blog, we’ll replace the in-memory storage with Redis and integrate this into a FastAPI application.

So… What’s the Catch?

At first glance, this algorithm looks perfect.

It’s fast.

It uses very little memory.

The implementation is straightforward.

So why do production systems use more complicated algorithms?

The answer lies in something called the boundary problem.

The Boundary Problem

Suppose your limit is:

5 requests per minute

A user sends five requests at the very end of a minute.

12:00:58
12:00:58
12:00:59
12:00:59
12:00:59

Everything is fine.

The user has reached their limit.

Now the clock moves forward by just one second.

A new window begins.

The counter resets to zero.

Immediately, the user sends another five requests.

12:01:00
12:01:00
12:01:00
12:01:01
12:01:01

From the algorithm’s perspective, everything is still valid.

The first five requests belonged to one window.

The next five belong to the next window.

But if you look at what actually happened, the server processed:

10 requests

in roughly

3 seconds

even though the configured limit was only:

5 requests per minute

That’s the biggest weakness of Fixed Window.

The algorithm only understands calendar windows.

It doesn’t understand that those two windows were only a second apart.

As a result, users can send large bursts of traffic whenever one window ends and another begins.

For many applications, that’s acceptable.

For others—especially APIs that need smoother traffic—it’s a serious limitation.

Should You Use Fixed Window?

Despite its shortcomings, Fixed Window is still used in many real-world systems.

It’s a good choice when:

  • You need something simple.
  • Memory usage is important.
  • Occasional bursts are acceptable.
  • You want the fastest possible implementation.

However, if you need more accurate rate limiting without these boundary spikes, we’ll need a different approach.

And that’s exactly what we’ll build next.

In the next section, we’ll look at Sliding Window Log, an algorithm that fixes the biggest weakness of Fixed Window by tracking when each request actually happened instead of just counting them.

Sliding Window Log

In the previous section, we learned about Fixed Window and its biggest limitation—the boundary problem.

A user could send:

5 requests at 12:00:59

and then immediately send another:

5 requests at 12:01:00

Even though your limit was 5 requests per minute, your server still processed 10 requests in about two seconds.

So the obvious question is:

Can we design an algorithm that always looks at the last 60 seconds, instead of dividing time into fixed one-minute windows?

That’s exactly what Sliding Window Log does.

The Core Idea

The biggest change is surprisingly simple.

Instead of storing how many requests a user has made, we store when each request happened.

That’s it.

That single change completely removes the boundary problem.

With Fixed Window we stored something like this:

user_42

count = 5

The algorithm only knows that the user made five requests.

It has no idea when those requests happened.

Sliding Window Log stores something very different.

user_42

[
12:00:05,
12:00:12,
12:00:18,
12:00:31,
12:00:45
]

Every request gets its own timestamp.

Now we know exactly when every request happened.

How the Algorithm Works

Suppose the limit is:

5 requests per minute

A new request arrives at:

12:01:10

The first thing we do is remove every timestamp that’s older than one minute.

So if our list looks like this:

[
12:00:02,
12:00:15,
12:00:35,
12:00:50,
12:01:01
]

the timestamp:

12:00:02

is now older than sixty seconds, so we remove it.

Our list becomes:

[
12:00:15,
12:00:35,
12:00:50,
12:01:01
]

Now we count how many timestamps remain.

4 requests

Since our limit is:

5 requests

we can safely allow the new request.

Finally, we append the current timestamp.

[
12:00:15,
12:00:35,
12:00:50,
12:01:01,
12:01:10
]

Every request follows exactly the same process.

  1. Remove expired timestamps.
  2. Count remaining requests.
  3. Reject if the limit has been reached.
  4. Otherwise, append the current timestamp.

Because the algorithm is always looking at the last 60 seconds, there are no artificial window boundaries anymore.

Python Implementation

Here’s a simplified implementation using plain Python.

from collections import defaultdict
from time import time

LIMIT = 5
WINDOW = 60

requests = defaultdict(list)


def allow_request(user: str) -> bool:
    now = time()

    requests[user] = [
        timestamp
        for timestamp in requests[user]
        if timestamp > now - WINDOW
    ]

    if len(requests[user]) >= LIMIT:
        return False

    requests[user].append(now)
    return True

The implementation is still fairly straightforward, but notice that we’re storing a list of timestamps instead of a single counter.

Using the limits Library

If you’re using the limits package, you don’t need to implement the algorithm yourself.

from limits import storage
from limits.strategies import SlidingWindowCounterRateLimiter
from limits import RateLimitItemPerMinute

store = storage.MemoryStorage()

limiter = SlidingWindowCounterRateLimiter(store)

limit = RateLimitItemPerMinute(5)

user = "user_42"

if limiter.hit(limit, user):
    print("Request Allowed")
else:
    print("Rate Limit Exceeded")

When we move to FastAPI in the next blog, we’ll simply swap the in-memory storage for Redis.

The Trade-Off

At this point you might be thinking:

“Why not always use Sliding Window?”

It’s definitely more accurate than Fixed Window.

But accuracy isn’t free.

With Fixed Window, we only stored one integer.

user_42

count = 5

That’s almost no memory.

Sliding Window Log stores something like this.

user_42

[
timestamp1,
timestamp2,
timestamp3,
timestamp4,
...
]

Now imagine a user sending:

10,000 requests

For a short period of time, the server might need to keep all 10,000 timestamps in memory.

As traffic grows, memory usage grows too.

That’s the biggest downside of this algorithm.

More Work Per Request

Every incoming request also performs more work than Fixed Window.

For each request we need to:

  • Remove expired timestamps.
  • Count the remaining timestamps.
  • Append the new timestamp.
  • Save the updated list.

Compared to simply incrementing a counter, that’s a lot more processing.

This is why Sliding Window Log is more accurate, but also more expensive.

Token Bucket

So far, both algorithms we’ve discussed have focused on counting requests.

Token Bucket takes a completely different approach.

Instead of counting requests, imagine every user owns a bucket.

That bucket can only hold a certain number of tokens.

Let’s say the bucket capacity is:

10 tokens

Every incoming request needs one token.

If there’s a token available, the request is allowed.

If the bucket is empty, the request is rejected.

Simple enough.

But here’s the interesting part.

Tokens automatically refill over time.

For example:

1 token every second

If the user stops making requests for a while, the bucket slowly fills back up until it reaches its maximum capacity.

This allows users to make occasional bursts of requests without violating the long-term rate limit.

How It Works

Let’s assume:

Bucket Capacity = 5

and

Refill Rate = 1 token/second

Initially, the bucket is full.

Tokens = 5

A user immediately sends three requests.

Tokens = 2

Now the user waits three seconds.

During those three seconds, three new tokens are added.

Tokens = 5

The bucket is full again.

This refill process continues automatically throughout the lifetime of the application.

Python Implementation

A simplified implementation looks like this.

from time import time

CAPACITY = 5
REFILL_RATE = 1

buckets = {}


def allow_request(user):
    now = time()

    tokens, last_refill = buckets.get(
        user,
        (CAPACITY, now)
    )

    elapsed = now - last_refill

    tokens = min(
        CAPACITY,
        tokens + elapsed * REFILL_RATE
    )

    if tokens < 1:
        buckets[user] = (tokens, now)
        return False

    buckets[user] = (tokens - 1, now)
    return True

The implementation is slightly more involved than Fixed Window because we also need to remember when the bucket was last refilled.

Using the limits Library

from limits import storage
from limits.strategies import TokenBucketRateLimiter
from limits import RateLimitItemPerMinute

store = storage.MemoryStorage()

limiter = TokenBucketRateLimiter(store)

limit = RateLimitItemPerMinute(60)

user = "user_42"

if limiter.hit(limit, user):
    print("Request Allowed")
else:
    print("Rate Limit Exceeded")

Why Is Token Bucket So Popular?

The biggest advantage of Token Bucket is that it naturally supports bursts.

Suppose your API allows:

60 requests per minute

Most users won’t send exactly one request every second.

Instead, they might make several requests together, then remain idle for a while.

Token Bucket handles this pattern beautifully.

As long as there are tokens available, requests are processed immediately.

This makes it a popular choice for:

  • API Gateways
  • Cloud Platforms
  • Reverse Proxies
  • AI APIs
  • Microservices

It offers a great balance between performance, fairness, and flexibility.

In the next section, we’ll look at the final algorithm—Leaky Bucket. Instead of allowing bursts like Token Bucket, it smooths incoming traffic into a steady flow, making it ideal for request throttling.
